The prior campaign ran about 11–17 FPS, roughly 59–91 ms/frame. Source baseline was 48522d0. Saved p48160 instrumented that rendering with per-evaluation phase clocks. Texture lookup alone took 18–19.5 ms/evaluation in capture-off windows. Evidence: `local/wwii-record-cost/campaign-baseline/{status-48160.log,phase-summary.json}`, prior `local/wwii-perf-audit-0f114d54/probe-results.txt`, and latest COMMS. The native 100+ FPS report and mission-select 111 FPS are not a matched campaign bridge-only baseline.

**Savings below are engineering estimates, not measurements of the new candidate.** Parent and child timers overlap: descriptor-write includes lock waiting; the draw callback includes DLAA preparation; Present includes translator waiting. Never add them twice. CPU NGX Evaluate duration is not its GPU inference duration. Separate processor-time savings from whole-frame wall-time savings. Items replacing a subsystem are alternatives to optimizing that same subsystem, not additional savings on top.

### Implementation details that must survive optimization

- Opus owns `observe/producers.cpp`, descriptor/copy/root/draw tracking and submission work. Astra owns the already-posted drain correction; no parallel rewrites of the file. Post handoff heads before combining.
- Cache stable *descriptions and lookup results*, not stale descriptor contents, current pose, or resource state. Track resource retirement, command-list reset/generation and descriptor updates. Avoid globally invalidating unrelated data for a change to one binding.
- Keep the submitted-frame ordering repair. Removing Flush blindly would exchange CPU time for missing/incorrect DLAA frames. Attribute blocking before modifying it.
- Camera bytes come from CPU-visible upload memory today, not synchronous GPU readback. Microsoft warns that reading write-combined upload memory can be slow. Favor a small cached CPU copy of the precise current camera data; do not shadow whole upload rings or rescan every draw.
- Use current frame/resource/version keys to reuse camera work. Correct one-ULP origin discrepancies and observed variant layout fields with saved evidence, rather than inventing a zero origin. Keep game-specific offsets inside the WWII adapter; shared caching/versioning belongs in general code.

### Concrete provider/handoff agreement

1. Opus emits current-frame input facts from native DX11 context execution. Include scene colour/depth subresources and active extents, actual insertion boundary, camera content/version and jitter identity. Recognize the calls actually used: instanced/indirect draws, dispatch/copy readers, deferred-context command lists and offset constant-buffer bindings. Do not equate largest RTV or Present with a proven scene boundary.
2. Astra maps those facts to the existing frame/evaluation contract and DX12 resources. Same physical adapter; owned shareable intermediates when game resources were not created shareable. Use format-compatible copies or existing conversion/resolve shaders. Separate input colour from output colour, especially if this later handles upscaling.
3. Use one fence timeline per producer direction, shared once. Submit DX11 input work before the DX12 wait; submit completion before the DX11 consumer waits. Reuse slots only after GPU completion, without a CPU completion wait in live callbacks. Keep resource states, in-flight references and teardown explicit.
4. Ordinary route performs input-colour copy, depth copy/conversion and output copy/composition. Sharing avoids CPU image transfer; it does not make these operations free. Avoid image readbacks and per-frame shared resource creation.
5. Opus applies jitter where native DX11 scene rendering uses it. Astra verifies projection/motion conventions using existing math tests. The same current scene must supply colour, depth, camera and jitter. Retain correct UI and later scene consumers.
6. One module owns activation: D3D11On12 fallback or native provider. DX12-native games keep the existing route. Do not disable observation on the current bridge until replacement input facts exist. Do not introduce DXVK/Vulkan as a third implementation.
