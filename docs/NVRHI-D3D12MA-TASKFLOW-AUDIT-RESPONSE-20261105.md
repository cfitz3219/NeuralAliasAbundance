# NVRHI + D3D12MA + Taskflow audit response — 5 November 2026

Cort supplied Downloads/nvrhi_d3d12ma_taskflow_audit.md for assessment. Its proposed assignments, mandatory stages and estimates are recommendations, not new implementation authority. Existing NVRHI/effect integration continues; Taskflow and D3D12MA remain proposed pending the requested Opus assessment. No game actions.

## Assessment

The combination is useful and fits our core: NVRHI manages eligible owned GPU recording/bindings, D3D12MA can supply backing allocations for our resources, and Taskflow can organise independent background CPU jobs. Preserve native inline recording and existing recording/submission lifetimes. The main recommendation is accepted; these corrections make it implementable.

1. **CPU performance figures are not measured outcomes.** The 35-to-165 FPS restoration, 0.2–0.4 ms descriptor saving, halved compilation time and 15–80 us wake cost are unsupported for this source/package. Observer CPU repairs already landed in later production code. Do not repeat the old optimization programme or defer current authorized work because the audit labels it stage zero. Benchmark the actual remaining cost.
2. **Default memory reservation claim is wrong for current upstream.** D3D12MA header ALLOCATOR_DESC documents 64 MiB preferred blocks, not 256 MiB. Default pool initialization sets minimum block count zero, allocating backing blocks as needed, not automatically reserving three 256 MiB heaps. UPLOAD/READBACK usually use system memory on a discrete GPU; counting every heap type as dedicated VRAM is wrong. Small preferred blocks are a policy to measure, not protection by themselves. Use actual adapter budget, allocation size, heap tier and pool statistics. A 3440x1440 RGBA16F texture alone has 37.8 MiB of texels before alignment, so forcing every allocation into a 32 MiB block cannot pool it.
3. **Pooling reduces allocation churn; it does not remove driver work.** A new placed resource still needs resource creation, and an exhausted pool needs another heap. Committed allocations remain appropriate for some large or special resources. Keep fallbacks. Do not promise zero mode-switch/resize overhead or universal savings from 64 KiB padding. The allocator supports small/tight alignments where available.
4. **The decisive lifetime requirement is missing from the simple three-layer diagram.** NVRHI importing a native resource does not retain its D3D12MA suballocation reservation automatically. Retain the allocation owner through every submitted NVRHI use AND every native recording lease using it. GC is not a per-resource completion certificate and does not track arbitrary native submissions. Release native/NVRHI resource references before their D3D12MA allocation, after the actual owning fences pass. Our new Recording::Retain and existing leases provide the relevant retention seams; no second competing native retirement system.
5. **Non-zeroed memory needs initialization.** Do not apply NOT_ZEROED universally just for speed. Every sampled texel, mip, counter, border and history region needs a first-use clear/copy/full write, including disabled paths, subrect padding and after resizing. D3D12MA placed allocations already do not promise zero contents. This is a first-use correctness condition, not a new visual gate.
6. **NVRHI ownership guidance is right, but classify each call site.** The pinned API has no open external command-list import. Host-owned render-small and standalone NR are eligible; J2 inline stays native, and J2-between currently remains native to preserve its single mixed original-game submission. The overlay owns its own lists, so native ImGui is a practical retained integration, not proof that overlay recording is intrinsically game-owned. Allocation pooling can be shared independently of list ownership. Correct NVRHI API names are createHeap/getTextureMemoryRequirements/bindTextureMemory or createHandleForNativeTexture; there is no allocateTextureMemory in the pinned interface.
7. **Taskflow recommendation is good with a few concrete additions.** Upstream defaults to hardware_concurrency workers; explicitly cap one shared background executor to one or two workers and below-normal priority. Replace/consolidate existing workers where appropriate, rather than adding a second pool alongside each module's old threads. Never wait for tasks in live render callbacks. Keep observation decoding's submission order, immutable snapshots and bounded backlog; parallelise independent analysis and merge in order. A task finishing does not mean GPU readback finished. Graphics API work needs HostWorkScope on the actual worker thread, not merely the submitting thread. Below-normal priority does not guarantee never preempting the game. E-core affinity is optional machine policy, not a universal dependency.
8. **Taskflow shutdown must be explicit.** Executor destruction waits for tasks and joins workers. Do not use the audit's global-static example as the actual DLL lifetime model. Stop intake and cancel/drain bounded background work in the existing orderly shutdown, outside loader-lock/static teardown and render callbacks. Keep cancellation, task data and shader/resource owners alive until their tasks finish.

9. **Pin Taskflow and its build requirements.** Current upstream4.1 uses C++20; our core currently builds as C++17. Compile the isolated background-service target as C++20, or deliberately select a compatible release, rather than accidentally changing every target through dependency CMake settings. This is a straightforward build boundary, not a reason to reject Taskflow. Primary build source: https://github.com/taskflow/taskflow/blob/master/CMakeLists.txt .

## Focused recommendation

Finish the current shared NVRHI service and effect integration first. Then use one existing scratch factory as the D3D12MA pilot, with allocation and heap counts, resize latency and peak/inflight memory measured on the same workload. Keep one allocator per actual game device, all its own calls under HostWorkScope, preserving current submitted owners. Add Taskflow to consolidate existing shader preparation/background jobs if Opus identifies a concrete workload with useful parallelism. Start with two below-normal workers and no per-draw task graph. No whole-engine replacement, forced new per-game adapters or guessed FPS target.
